## Desired architecture

The conceptual pipeline should become:

```text
event
  ↓
persist + dedup
  ↓
deterministic filters
  ↓
decision model
  ↓
structured semantic judgment
  ↓
deterministic policy
  ↓
ignore | notify | act | delegate
                         ↓
                  generative agent
                         ↓
                  structured result
                         ↓
                    new mrmr event
                         ↓
                    decision model
                         ↓
                       policy
```

The important point is that the agent is not the root of the system.

mrmr is the root runtime.

The agent is one possible effect of a policy decision.

Also preserve the distinction between:

- **decision**: bounded judgment about what is happening
- **investigation/work**: open-ended but scoped task execution
- **authority**: deterministic runtime policy deciding what is allowed

## Change 1: add a first-class decision-model provider abstraction

mrmr currently supports OpenAI-compatible structured generation and TypeSafe Jev.

Refactor or extend the model layer so that decision models are a first-class concept rather than being treated as just another text-generation backend.

The system should be able to represent questions such as:

- Choice
- Yes/No
- Score

A decision provider should return normalized typed results that policy can address consistently.

Design a provider interface clean enough that the following backends could exist:

- TypeSafe Jev
- Liquid d1
- future local decision-model implementations

Do not necessarily implement every provider if API details are unavailable, but create the correct abstraction and implement at least one local/OpenAI-compatible path if feasible.

If Liquid d1 exposes an OpenAI-compatible or known API that can be implemented cleanly from available information in the repo or public docs already referenced in comments/config, support it. Otherwise create a clearly separated provider interface plus a `liquid-d1` configuration shape and leave the transport as a documented TODO rather than inventing an API.

The key architectural requirement is that policy consumes **normalized decision results**, not backend-specific response shapes.

For example, a normalized choice should conceptually expose fields such as:

```json
{
  "choice": "needs_investigation",
  "probabilities": {
    "routine": 0.03,
    "resolved": 0.02,
    "needs_investigation": 0.92,
    "immediate_attention": 0.03
  },
  "confidence": 0.92
}
```

Do not assume confidence and probability are universally identical. Preserve backend-native data when useful, but provide a stable normalized surface.

## Change 2: explicitly separate "judge" models from "worker" models

Configuration should make the distinction obvious.

Something conceptually like:

```yaml
models:
  judge:
    role: decision
    provider: ...
    model: ...

  worker:
    role: agent
    provider: openai-compatible
    base_url: ...
    model: LFM2.5-2.6B
```

Exact naming is up to you if a better schema fits the current design.

The interpreter stage should use a decision-capable model.

Delegated work should target an agent/worker endpoint.

Avoid over-engineering model routing at this stage.

## Change 3: make delegated agent completion able to re-enter mrmr as an event

This is the most important behavioral change.

Today, README states:

> Agent completion does not automatically return as a new event.

Add an explicit, safe mechanism for a delegated agent result to become a new mrmr event.

This must not create an unconstrained agent loop.

Design it as an **event loop driven by externally completed work**, not an LLM self-loop.

Conceptually:

```text
delegate
  ↓
agent endpoint
  ↓
agent returns structured completion
  ↓
mrmr emits:
agent.completed
  ↓
normal ingestion pipeline
```

The returned event should contain enough provenance to trace:

- originating event ID
- delegation target
- causal depth
- agent result
- completion status
- optional structured evidence
- optional proposed next action
- timestamps if available

Reuse the existing causal-depth protection.

Keep the existing maximum depth guard or improve it if needed.

Agent completion re-entry must be explicitly configurable, for example:

```yaml
delegate:
  agent: homelab
  prompt: "Investigate this event."
  emit_completion: true
  completion_event_type: agent.investigation.completed
```

Do not make every delegation automatically recursive by default.

Default behavior should remain safe.

## Change 4: support read-only investigation patterns cleanly

mrmr should make it natural to delegate bounded investigation without granting the model mutation authority.

The runtime does not need to implement an entire tool framework.

Instead, formalize the contract between mrmr and an external agent endpoint.

The request should include:

- event
- decision
- task/prompt
- delegation metadata
- permissions or capability hints if configured

The response should ideally be structured.

Design a completion schema such as:

```json
{
  "status": "completed",
  "summary": "...",
  "findings": [...],
  "evidence": [...],
  "recommended_action": "...",
  "metadata": {}
}
```

Do not require every field if that would make the adapter brittle.

Preserve compatibility with simple HTTP 2xx "accepted" agent endpoints if possible.

If necessary, support two modes:

- fire-and-forget
- synchronous structured completion

Prefer an incremental design over replacing the current delegate adapter wholesale.

## Change 5: strengthen the event provenance model

Ambient systems need excellent traceability.

Every model-driven or agent-generated event should be inspectable.

Add or formalize provenance fields so the runtime can reconstruct:

```text
source event
  ↓
decision
  ↓
policy rule
  ↓
delegation
  ↓
agent completion
  ↓
follow-up decision
  ↓
effect
```

Avoid duplicating large payloads unnecessarily.

Use IDs/references where practical.

Make sure `mrmr inspect` remains useful.

If there is a natural place, enhance trace output to show parent/child relationships.

## Change 6: preserve deterministic authority

Do not let model output directly define:

- arbitrary URLs
- shell commands
- new permissions
- new adapters
- arbitrary tool names
- executable HTTP destinations

Models may return semantic values like:

```text
recommended_action = restart_service
```

but policy/configuration must map that to an allowed predefined effect.

Example:

```yaml
policy:
  - if:
      result.remediation.choice: restart_candidate
      result.remediation.confidence: "> 0.9"
    then:
      action:
        type: http
        target: restart-plex
```

The model should never return the actual target URL.

Keep mrmr's existing safety posture intact.

## Change 9: documentation language

Update the README to make mrmr's architecture explicit.

The core positioning should be approximately:

> mrmr is a local-first, event-driven runtime for ambient AI.
